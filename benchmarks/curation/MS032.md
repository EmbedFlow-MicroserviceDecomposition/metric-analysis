## Decisions
| # | Decision | Basis |
|---|---|---|
| D1 | Asynchronous messaging counts: publisher method → subscribing handler, protocol `Messaging`; handlers are exposed interfaces | Team decision (Ravishan), applies to all systems |
| D2 | One call entry per distinct (src_class, src_method, dst_interface_id) | Team decision; matches MS001 |
| D3 | Gateway routes defined only in config are not calls; edge-service has no interfaces | Precedent: MS001 (verified) excludes its config-routed gateway. Note: `schema.json` allows protocol `GatewayRoute` — raised with Yumeth |
| D4 | src_class of the REST call is the client wrapper `UserClient`, not its caller `FriendService.create` | Precedent: MS001 uses `CustomersServiceClient` etc. |
| D5 | Messaging src_class is the controller (`UserController`, `FriendController`) | The `messageBroker.output().send(...)` call is written inside the controller methods (in callbacks passed to the service layer) |
| D6 | `FriendController.addFriend` return type = `Friend` (declared `Mono<?>`) | `friendService.create(...)` returns `Mono<Friend>`; the trailing `.then()` belongs to the callback argument (`FriendController.java:85,105`, `FriendService.java:49`) |
| D7 | `createUser` param `Mono<User>` → `User`; handler params `Message<XEvent>` → `XEvent`; `Flux<T>` → `List<T>`; `Mono<Void>` → `void` | Normalisation rules in `prompts/claude_code_prompt.md` |

## Runtime check (2026-11-18)
Ran the published images (`hyperskale/*`, pushed 2022-11-26, same day as the last code commit) with `docker compose`. The override pins infrastructure only (cp-kafka/zookeeper 7.5.3, postgres 15) and runs the amd64 images under emulation; service images and config are unchanged. `scenario.sh` calls all 9 REST endpoints through the gateway. Evidence is in `MS032_runtime/`.

**Captures:** tcpdump on each domain service's inbound port, with source IP mapped to container; Kafka console consumers on `user` and `friend`; consumer-group inspection; recommendation-service handler logs.

| GT call | Observed at runtime | Result |
|---|---|---|
| 1 friend `UserClient.getUser` → user `GET /v1/users/{id}` | 6 requests from friend-service's IP (2 per addFriend × 2 successful + 2 for the unknown-user case) | ✅ confirmed |
| 2 user `createUser` → `UserProcessor.apply` | 6 `USER_CREATED` on topic `user`, 6 `Event received … USER_CREATED` in recommendation-service | ✅ confirmed |
| 3 user `updateUser` → `UserProcessor.apply` | 2 `USER_UPDATED` produced and handled | ✅ confirmed |
| 4 friend `addFriend` → `FriendProcessor.apply` | 4 `FRIEND_ADDED` produced and handled | ✅ confirmed |
| 5 friend `removeFriend` → `FriendProcessor.apply` | 2 `FRIEND_REMOVED` produced and handled | ✅ confirmed |

**No unlisted edges:** every other inbound HTTP request to the 3 domain services came from edge-service (gateway forwarding, excluded by D3). The only consumer groups on `user`/`friend` are recommendation-service's (`user-group`, `friend-group`, client 172.18.0.8). The recommendation queries returned correct mutual friends and recommendations, which shows the Kafka projection works end to end.

**D6 confirmed:** `POST …/addFriend` returned a `Friend` JSON body (HTTP 201).

**Known environment issue (not a call-graph issue):** recommendation-service health reports DOWN because its Neo4j 4.4 driver's reactive health check is unsupported by the `neo4j:3.5.0` server set in the compose file. The service started, subscribed to both topics and served queries.

**Limit:** runtime observation confirms that the listed edges really happen and that no other edge was triggered by these 9 endpoints. It cannot rule out paths not exercised, but all 9 REST entry points were exercised.

Gate self-test: 7 deliberately broken copies of the ground truth were all caught (short class name, wrong service, unknown interface, wrong line number, fabricated snippet, deleted call, deleted handler).
