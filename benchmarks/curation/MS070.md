## Method: type-checked static analysis
Grep cannot resolve Go gRPC calls reliably (the client's *type* decides the destination), so `MS070_analysis/main.go` type-checks all non-test boulder packages with `go/packages` (Go 1.27 in Docker, vendored deps, cgo on, **0 load errors**) and reports, by type: every call taking `...grpc.CallOption` (115), gRPC client methods passed as function values (5 boulder + 2 gRPC plumbing), calls from service code into the call-making libraries `ctpolicy`, `goodkey.GoodKey`, `csr.VerifyCSR` (13), and all 18 server registrations with their implementing types. `protos.py` lists the 111 RPCs of the 15 gRPC services.

## Decisions
| # | Decision | Basis |
|---|---|---|
| D1 | One interface per (registered implementing type, RPC of the gRPC service it is registered for); endpoint = the gRPC full method name. The SA proto repeats its read-only RPCs in `StorageAuthority`, so e.g. `SQLStorageAuthority.GetRegistration` (`/sa.StorageAuthority/GetRegistration`) and `SQLStorageAuthorityRO.GetRegistration` (`/sa.StorageAuthorityReadOnly/GetRegistration`) are separate interfaces: they are separate gRPC endpoints | Registrations in `cmd/boulder-sa/main.go:106,111`; same "serving class" principle as MS021 D2 |
| D2 | A call's destination is decided by the **constructor** used in the caller's `main()`: wfe2, sfe and crl-storer build `NewStorageAuthorityReadOnlyClient` → `SQLStorageAuthorityRO`; ra, crl-updater and ca build `NewStorageAuthorityClient` → `SQLStorageAuthority` (ca's field has the narrower `StorageAuthorityCertificateClient` type) | `cmd/*/main.go` |
| D3 | Params = [request message], return = response message (no package prefix); streams become `List<T>` | Normalisation rule |
| D4 | HTTP front ends: one interface per handler method; a method serving several routes lists them all (`WebFrontEndImpl.Certificate`: `/acme/cert/`, `/get/cert/`; `makeOverrideRequestFormHandler`: 4 override forms). Static-file, debug/metrics and gRPC-health handlers are not interfaces | `wfe2/wfe.go:454-479`, `sfe/sfe.go:155-183` |
| D5 | **Library-mediated calls** go to the in-service invoker (MS021 D1 rule): `ctpolicy` → publisher is attributed to `ra.GetSCTs` and `ra.issueCertificateInner`; the key-policy blocked-key check (`goodkey` → `sa.KeyBlocked`, a client method passed as a function value in `main()`) to `ca.IssueCertificate`, `ra.NewRegistration`, `ra.validateFinalizeRequest`, `wfe2.validSelfAuthenticatedPOST`, `wfe2.validKeyRollover`. Each call's evidence cites the service line, the library line and the `main()` wiring | Type-checked library-caller list; it matched the hand mapping exactly |
| D6 | **Rate-limit override refresher excluded as configuration loading**: with `OverridesFromDB` on, ra and wfe2 hand `GetEnabledRateLimitOverrides` (SA read-only) to a `ratelimits` background refresher wired in `main()`, which reloads the overrides every 30 minutes. No service type invokes it. It is **on in `test/config-next`** and off in `test/config` (which uses an overrides file). Treated like MS020's config-server fetches. *Correction:* this was first approved on my wrong claim that it is off in every shipped config (I had checked the key with the wrong case); the blind extraction caught it, and Ravishan re-decided with the corrected fact | Ravishan's decision (2026-11-18, re-confirmed) |
| D7 | Not calls: va → remote VA perspectives (same va type); `admin`, `cert-checker`, `ceremony`, `crl-checker` (CLIs/batch); mocks, `sa/satest`, `test/`; gRPC health and interceptors; external systems (CT logs via publisher, S3 tiles from mtca/mtpublisher, Salesforce Pardot from email-exporter, Zendesk from sfe, DNS/HTTP validation targets) | non_services / external / same-service rules |
| D9 | Application health/readiness endpoints written in the service's own code are interfaces (wfe2 `Healthz`; consistent with MS021's `ReadyRest.isReady`); framework, debug and metrics endpoints are not | Ravishan's decision (2026-11-18), applies to all systems |
| D8 | **Dead wiring**: sfe builds an SA read-only client (`cmd/sfe/main.go:157`, stored at `sfe/sfe.go:59,111`) but never calls it, so there is no sfe → sa edge | Type checker: no call or method value on it |

## Runtime check (2026-11-18)
**Why metrics, not packet capture:** boulder's gRPC traffic is mutual TLS, so packets cannot show method names; tracing is configured only for a few components. Every boulder process does export Prometheus gRPC metrics (`grpc_client_handled_total` / `grpc_server_handled_total` per gRPC service and method) on its debug port, so **each running process reports exactly which RPCs it called**.

**Setup:** boulder's own dev environment (`docker-compose.yml`) with the image tags its CI pins (`boulder-tools:go1.27.2_2026-10-14`, `vtcomboserver:vitessv24.0.3_2026-09-24`, `sunlight:sunlightv0.10.0_2026-09-24`), amd64 under emulation, run from a scratchpad copy because the build writes into the tree. `runtime_check.py` performs the same steps as `test/integration-test.py --chisel --gotest` (build, start all 32 server processes from `test/startservers.py`, chisel ACME client tests, boulder's Go end-to-end tests) and then always runs `scrape_metrics.py` while the servers are up, even if a test fails. `compare.py` maps processes to services (remoteva → va, ra-sct-provider → ra) and gRPC methods to ground-truth interfaces by endpoint.

**Runs:**
- Run 1: build 76 s, Go tests passed (105 s). My wrapper passed `None` as the chisel filter, so chisel did not run, and my scraper read wfe2 and sfe on the wrong port (boulder's server list puts wfe2's ACME port 4001 and sfe's 4003 in the debug-port slot). Both were fixed.
- Run 2: chisel passed (106 s). The Go tests ran, with 2 failures (`TestIPCNRejected`, `TestDuplicateFQDNRateLimit`): HTTP 429 rate limits left over from run 1, because boulder's `test.sh` flushes Redis before a run and my re-run did not. This is test state, not call-graph behaviour.
- Results below are the union of both runs (`union_runtime_vs_gt.txt`).

**Result:**
- **55 of the 77** ground-truth (caller service, destination interface) pairs observed directly in client-side metrics, and **0 observed client calls outside the ground truth**. The only other client calls are va → remote VA perspectives (same service, D7).
- **crl-updater** runs as a one-shot process during the tests, so its client metrics are gone before the scrape. **5 of its 6** RPCs (`GenerateCRL`, `UploadCRL`, `GetRevokedCertsByShard`, `LeaseCRLShard`, `UpdateCRLShard`) were each received 3,120 times server-side, and no other ground-truth caller targets them. `GetLatestRevokedCertByShard` was not exercised.
- **Reverse check:** every RPC any boulder server received during the tests is the target of at least one ground-truth call, so no received call lacks a caller in the ground truth, including from processes that could not be scraped.
- **16 pairs not exercised** by the test suite: the MTC paths (ra → mtca `Issue`, → mtcb `StandaloneReady`, → sa `FinalizeMTCOrder`); rate-limit override and pause/unpause flows (sfe → ra `AddRateLimitOverride`/`UnpauseAccount`, ra → sa `AddRateLimitOverride`/`PauseIdentifiers`/`UnpauseAccount`); wfe2 and sfe → email-exporter `SendContacts`; the flag-dependent wfe2 → ra `GetOrder` (wfe2 → sa-RO `GetOrder` was observed); ra → sa `GetOrder`/`RevokeAuthorizationsFor`/`SetAuthzProcessing`; wfe2 → sa-RO `GetSerialMetadata`; crl-storer → sa-RO `GetSerialsMetadata`. These rest on code evidence (Gates B/C) and the blind extraction.

**Limit:** metrics identify the caller *service* and the destination *RPC*, not the caller class/method; those come from the type-checked code evidence.
