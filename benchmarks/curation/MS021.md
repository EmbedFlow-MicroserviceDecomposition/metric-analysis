## Decisions
| # | Decision | Basis |
|---|---|---|
| D1 | Calls made through the registryclient library are attributed to the **in-service caller** (e.g. webui `ProductServlet.handleGETRequest` → persistence `ProductEndpoint.findById`), treating the library like Feign/WebClient. Library "services" get no edges | Ravishan's decision (2026-11-18). The library is packaged in each service; taking it literally would make an undeployed library the hub and give webui no outgoing calls |
| D2 | Endpoints inherited from `AbstractCRUDEndpoint` (in the library) are recorded **per concrete subclass** (`ProductEndpoint.findById` = `GET /rest/products/{id}`, …), 5 methods × 5 resources | Ravishan's decision (2026-11-18): distinct URLs and entity types |
| D3 | Same-verb overloads get a parameter-type suffix: `UserEndpoint.findById(Long)` (inherited, `/users/{id}`) vs `UserEndpoint.findById(String)` (`/users/name/{name}`) | Extension of MS078 D2 (qualify only on collision) |
| D4 | Library operation → destination mapping, read from the library code: `getEntity` → `findById`; `getEntities` → `listAll`, or with a filter → `listAllForCategory`/`listAllForUser`; `getEntityWithProperties("users","name")` → `UserEndpoint.findById(String)`; `sendEntityForCreation` → `create`; `getWebImage(s)` → `getWebUIImages`; `getProductImage(s)`/`getProductPreviewImages` → `getProductImages`; `LoadBalancedStoreOperations.*` → `AuthUserActionsRest`/`AuthCartRest`. Each call's evidence cites the call site, the library line that builds the request, and the destination handler | `registryclient/rest/*.java` |
| D5 | Return types = actual response entity (auth → `SessionBlob`; image → `Map<…>`/`boolean`/`String`; recommend → `List<Long>`; inherited CRUD: create/update/delete → `void`, findById → entity, listAll → `List<entity>`; servlets → `void`) | Same principle as MS032 D6 / MS078 D6 |
| D6 | Servlet handlers are interfaces (`handleGETRequest`/`handlePOSTRequest`, `doGet`/`doPost`). webui servlets without their own `handlePOSTRequest` accept POST through `AbstractUIServlet`'s default (`AbstractUIServlet.java:271-273` delegates to `handleGETRequest`), so their endpoint is `GET|POST` | Code; confirmed at runtime (locust/scenario POSTs to `/cartAction` work) |
| D7 | Endpoints include the WAR context and JAX-RS application path (`/tools.descartes.teastore.<svc>/rest/...`); kieker.rabbitmq is deployed as `logs.war`, so it uses `/logs/...` | `web.xml` (`/rest/*`), kieker.rabbitmq `Dockerfile` |
| D8 | Not calls: registry discovery/heartbeats (RegistryClient); Kieker → RabbitMQ monitoring; Jaeger tracing; multicast to the same service's own replicas (persistence `CacheManager`/`DataGenerator`, recommender `TrainingSynchronizer.filterLists`); the locust load script | Existing infrastructure / same-service / external-client rules |
| D9 | **Dead call excluded:** webui `DataBaseActionServlet:84` multicasts `GET <recommender>/rest/train/async`, but `TrainEndpoint` has no `async` path, so there is no interface to receive it | Code (TrainEndpoint has only `/train`, `/train/timestamp`, `/train/isready`); runtime: HTTP 404 |

## Service list correction (2026-11-18)
Following Yumeth's rule (keep only real services in `codebases/microservices/microservices.json`, record the rest under `non_services` with a reason, add any newly found services), the MS021 entry went from 13 listed modules to **7 services**: registry, persistence, auth, image, recommender, webui and kieker.rabbitmq. kieker.rabbitmq stays because it is its own deployed image (`teastore-kieker-rabbitmq`, RabbitMQ plus a log viewer, used in the monitoring setup), in line with MS020's monitoring and turbine-stream-service (Ravishan's decision). The 6 moved to `non_services` are entities, kieker.probes and registryclient (libraries packaged into the services), dockermemoryconfigurator (container start-up helper), and dockerbase and docker.all (Docker packaging, no application code). No services were missing.

The partition was regenerated: 11 → 7 services and 161 → 124 classes. The 4 removed partition services (entities, kieker.probes, registryclient, dockermemoryconfigurator) had **no interfaces and no calls** in the ground truth, so the call graph is unchanged and only their empty keys were removed. Gates A–C pass; the mutation suite stays at 26/26.

## Runtime check (2026-11-18)
**Images:** `descartesresearch/teastore-*:development` (2023-12-07, native arm64). Between that date and the analysed commit (`34b37f7`, 2025-01-08), only two Java files changed (`dockermemoryconfigurator/Configurator.java`, `registryclient/tracing/Tracing.java`), and neither touches routes or calls (checked via the GitHub compare API).

**Setup:** `examples/docker/docker-compose_default.yaml` with the `:development` tags. registry, db and persistence started first and the persistence capture attached **before** image/recommender/auth/webui started, so their startup calls were recorded. tcpdump on port 8080 in all 5 application services; each request attributed by **source and destination IP** and deduplicated across captures; paths matched to the ground truth's interface endpoints.

**Scenario** (`scenario.sh`): index, login, category (+ page size), product, cart add/update/remove, checkout, order, profile, about, status, database, error, admin database regeneration, status, logout. The first checkout copied the repo's locust script, whose `adress1`/`adress2` field names are misspelt (the servlet expects `address1`/`address2`), so no order was placed. Checkout was re-run with the correct names (appended to `scenario.log`).

**Result** (`runtime_vs_gt.txt`): **32/32** ground-truth (src service, dst interface) pairs observed; **0** observed service-to-service requests outside the ground truth, apart from discovery traffic to registry (D8) and the single dead `GET …/train/async` (D9), which a direct request confirmed returns **HTTP 404** (`/train/isready` → 200). Startup traffic image → persistence (`generatedb/finished`, `categories`, `products/category/{id}`) and recommender → persistence (`generatedb/finished`, `orders`, `orderitems`) was observed as predicted.

**Limit:** network capture identifies the source *service* and destination *interface*, not the source class/method; those come from the code evidence (Gate B) and agree with the blind extraction (Gate D).
